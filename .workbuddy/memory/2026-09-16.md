## ⭐ 本轮最值钱的四条教训

### ① 长度判据必须按「显示宽度」，不是字符数 —— 且会**双向**失真

CJK 1 字符 ≈ 西文 2 宽。按 `len()` 统计时：
- **假报**：ja「会社概要 — SANFAN ヨガ・フィットネス」23 字被判 title 过短，
  实际 36 宽完全够用 → 17 处全是假的
- **漏报**：ja/ko 标题 79 字其实 158 宽（严重超长）却判正常

我第一轮统计就掉进漏报方向：报了「ja/ko 完全 0 超长」，换成宽度后
ja products 112 页、ko 60 页超长。**改度量前先问一句：这个 `len()` 对 CJK 成立吗。**

### ② 机械规则的第一版几乎一定误伤，必须先把「将被删除的内容」全列出来审查

- 后缀规则首版：`materials.html` 的 `|` 写成 HTML 实体 `&#124;`，
  字符类只认字面 `|` → 退到前一个 `—`，把核心关键词
  `TPE vs PVC vs PU vs Cork` 整段当品牌后缀删掉
- 删 OEM 段首版：只认字面 `|` → EN 一处都没改（81 处改动全落语言版）。
  又是同一种实体坑
- 收拢规则首版：只要求尾段含品牌名 → **EN 5 篇博客 + 各语言共 47 处中招**
  （`REACH, CA Prop 65 & 6P: Yoga Mat Compliance for US & EU — SANFAN`
  被切得只剩 `REACH, CA Prop 65 & 6P`，标题彻底毁掉）

**做法**：dry-run 后把「所有将被删掉的尾段」`Counter` 去重打出来逐条看。
第二轮 72 种尾部全是「SANFAN + 制造商量词」，一眼就能确认安全。

### ③ 多规则脚本要迭代到不动点，否则不幂等

规则 ③ 会把 `de/products.html` 从 84 宽削到 32 宽，而规则 ② 是
「按剩余空间选后缀」→ 下一轮又把后缀升级成长版。一轮跑完留一处改动不生效
（`--check` 报 1 处）。`norm_title` 改成循环到不动点（3 轮足够）即解决。

### ④ 审计脚本的假报会掩盖真问题，两类都要修

- **跨语言比较**：`titles`/`descs` 是全局字典按文本做键，
  `Ab Wheel — SANFAN Yoga & Fitness OEM` 在 EN 与 de 各出现一次即判重复。
  不同语言靠 hreflang 区分，同名完全正常 → 16 组里 15 组是假报。
  改成按 `(lg, title)` 分组
- **字符数 vs 宽度**：见 ①

修完后真露出 1 组真重复：`it/products/tpe-resistance-loop-band.html` 与
`it/products/resistance-band-2.html` 标题完全相同（HEAD 即如此）——
EN 是 `Resistance Band` vs `Resistance Loop Band`，DeepL 把后者也译成
`Fascia elastica di resistenza`，**漏掉了 "Loop"**。后者改为
`Fascia elastica ad anello`。（术语表待补：resistance loop band）

### ⑤ description 截断要有「不许丢什么」的闸门

首版只按「句末 + 宽度预算」截断 → 32 处里 **14 处**把 B2B 钩子切掉了：
- de 首页丢了 `Mindestbestellmenge 100 Stück, Muster in 7 Tagen, ROHS / CE`
- fr/pilates 丢了 `OEM/ODM avec votre logo`
- it/index 丢了 `quantità minima d'ordine (MOQ) 100 pezzi`

补上 `KEEP_RE`（MOQ / 打样 / OEM / logo / 认证 / 报价 / 联系方式，各语言词干）
且**只检查实际被丢弃的那一段**（不是全文）→ 32 → 21 处，被拦下的 11 处

**已落盘的错误改动必须回滚再重跑**，否则新规则只能拦住未来的、改不了过去的：

# 2026-09-16（下午）— 描述悬空 + 术语粘连第二家族 + 结构化数据中文泄漏

承接上午的 meta 规范化。上午的结论露出一个下游副作用，顺藤摸出三族新的机翻硬伤。

## 做了什么（四件事）

### 1. description「悬空」修复 —— `fix_desc_cut_20260916.py`

**病根**：`fix_desc_unique.py`（09-12）把 >165 字的 description 用 `fit()` 截断，
而 `fit()` 断在**最后一个空格**，不管句子边界；而且它只改
description / og / twitter 三个 meta，**从不碰 JSON-LD**。

后果：**381 页**（EN 64 / de 63 / it 60 / ko 52 / fr 54 / es 46 / ja 42）的
description 以半句收尾，7 个语言版本全中（工具缺陷随翻译管线原样传播）。

**修法**：JSON-LD 的 `description` 反而是**完整原文** → 拿它做对齐源，
用 `difflib.SequenceMatcher` 找最长公共块，把 meta 里公共块之后的悬空尾巴
换成 JSON-LD 的后续（不要求从末尾对齐 —— 首版按「meta 后缀出现在候选里」匹配，
de 有页面 meta 与 JSON-LD 是**两份不同译文**，句中就分叉，`MIN_OVERLAP=20` 直接失配）。

结果：**389 页 / 1117 处**（1061 处对齐拼接 + 54 处人工规则 + 2 处安全截断，
**0 处不可修**）。复扫悬空 = 0。

### 2. 术语粘连**第二家族** —— `term_repair.py` 规则表（单一来源）

上午修的是「小写词干 + 术语」粘连（`alfombrTPEes`）。这次发现方向**相反**的一族：
**术语 + 小写尾巴**（`PVCe` / `PVCund` / `PVCet` / `TPEe` / `PUe` / `EVAs` / `MattPUn`…）。
原扫描器 `GLUE_LOWER` 要求词干 ≥3 个小写字母，**系统性漏掉这一族** →
新增 `GLUE_TERMWORD` 扫描类型 + 约 30 条规则。

三种成因，三种修法（判据：**粘连尾巴本身是不是目标语言的词**）：
- 是词 → 补空格（es `PVCe`→`PVC e`、fr `PVCet`→`PVC et`、de `PVCund`→`PVC und`）
- 不是词 → 删掉（fr `TPEe`→`TPE`、it `PUe`→`PU`、de `Öko-TPEe`→`Öko-TPE`）
- 词内被**插**空格（镜像方向）→ 合起来（it `priv a`→`priva`、es `inodor a`→`inodora`）

`fix_glue_20260916.py` 落盘 **180 文件 / 510 处**；复扫 0，幂等 0。

### 3. 结构化数据里的中文 —— `fix_lang_leak_20260916.py`

**病根**：EN 页卡片用行内配对 span 双语：
`<h4><span class="lang-en">Alignment Line TPE Yoga Mat</span><span class="lang-zh">带体位线 TPE 瑜伽垫</span></h4>`
而 `build_category_pages.py` 的 `title_of()` 只做「剥标签 + 压空白」→ 得到**双语串**，
写进两处：JSON-LD `ItemList.itemListElement[].name` 和 `products.html` 缩略图的 `title`/`alt`。

翻译管线把 EN 半翻成 6 语言、中文半原样留着 →
`de/tpe-yoga-mats.html` 的 23 条 ItemList 里 **17 条**带中文。

**修法**：干净标题的唯一可信来源 = 该语言卡片 `<h4>` 里**第一个非 `.lang-zh` 的 span**，
按 slug 锚定回填（根目录先扫 = 优先级，`rb2` 取到与 `<title>` 一致的正确形态）。
结果 **78 文件 / 820 条 JSON-LD + 262 处缩略图 title·alt**；同时在
`build_category_pages.py` 里根治 `title_of()`。

### 4. `Figure 8` 被当成「插图 8」—— 6 语言全错

`Figure 8 Resistance Bands`（8 字形）被译成 de `Abbildung 8`（=插图 8）、
fr `Figure 8 :`、it `Figura 8:`、es `Figura 8:`、ja `図8`、ko `그림 8` —— **6 个语言版本全错**。
`term_repair.py` 加 9 条规则，落盘 **30 文件 / 156 处**；同时在
`translator.GLOSSARY` 加 EN 侧保护（防重译复发）。

## ⭐ 本轮新教训（都踩过）

### ① 审计工具必须**按顺序模拟**，独立匹配会**双向**失真

`audit_rule_ctx.py` 首版对**原始文件**逐条规则独立匹配，把
`<li>TPEo ecológico</li>` 报成 `TPE o ecológico`（看着像严重误改，实际真执行时
`Es 术语尾多余元音` 排在前面，`TPEo` 早被吃成 `TPE`）。
独立匹配既**夸大**规则间冲突，又**掩盖**规则顺序错导致的真冲突。
改成「边应用边匹配」后才与落盘结果一致（同一批规则命中数 329 vs 独立匹配的虚高值）。
**推论：关键字过滤只能决定「报不报」，不能决定「改不改」**（跳过的规则也要照常落盘）。

### ② 幂等自测抓到了双写 bug

`Figura 8:\s*Fasce elastiche` → `Fasce elastiche a forma di 8`，
而输入**已经是** `Figura 8: Fasce elastiche a forma di 8` → 产出
`…a forma di 8 a forma di 8`。短规则必须把**已经正确的尾巴**一起吃掉
（`(?:\s+a forma di 8)?`）。`test_term_repair.py`（新增，60 用例）当场拦下。

### ③ Python 替换串漏 `r` 前缀 = 静默注入控制字符

`"TPE \1"` 里 `\1` 被当成八进制转义 → U+0001，正则不报错、`repair()` 也不报错，
只会把控制字符写进页面。修法：全部 `r"…"` + `term_repair` 在 **import 期断言**
替换串不含控制字符（fail fast）。

### ④ 「删中文」不能靠字符判据

`de` 的紫款标题是 `Lila „TPE“-Yogamatte TPE` —— 中文那半**已经被引擎当英文翻掉了**，
没有中文可删，只剩残留 ` TPE`。按字符判据修不干净，必须拿**该语言自己的干净标题**重建。

### ⑤ 验收指标本身要先「剔除设计内内容」，否则数字没意义

非中日韩页面汉字残留：不剔「语言切换器 `中文` / `微信` / 中文模式 WhatsApp 预填」→
**950 页假命中**；而锚太窄（只认 `%E4%BD%A0%E5%A5%BD`=你好）又会漏掉
**630 个产品页**（它们的预填以 `%E4%B8%89%E6%A2%B5`=三梵 开头）。
改判据为「引号里有连续两个百分号编码字节就整条丢掉」后才清净。

### ⑥ 术语表只有 de/ja/ko → fr/it/es 各译各的

`GLOSSARY` 原先只有 de/ja/ko 三语，fr/it/es 同一品类词出现多种说法。
补三语共 84 条（**取自站内已上线且正确的页面**，不是新造）+
`resistance loop band`（09-15 记的欠账：it `Fascia elastica ad anello`）。

### ⑦ 全站扫描一律后台跑

前台跑 >120s 必被 SIGTERM（exit 137）。这轮又踩了两次才养成习惯。

### 超长 title：按「主体宽度」分档，而不是看全长

`title_split.py` 判据 —— Google **从尾部截断**，所以看**主体**：
- A 档 主体 ≥60：主体自己就被截半句 → **必须重写**（94 条）

不能当 bug 批量改 —— 这个判断错了会毁掉全站标题。

### 最后 1 条漏网标题的真病根：不是"太长"而是**页内自相矛盾**

`es/products/figure-8-resistance-bands.html` w=63，A/B 档都漏。
真因：`<title>` 写 `Bandas de resistencia`，而同页 og/twitter/h1 三处都写

- **③h 术语清单被压缩**：`SGS,REACHyCA Prop 65` ← EN 是 `SGS/REACH/CA Prop 65`。
  斜杠改逗号 + 逗号吞空格 + 西语连词 `y` 焊进 `REACH|CA` 之间。
  ⚠️ **规则顺序要紧**：`REACHyCA` 里的 `y` 是字母，会让逗号规则的 `\b` 失效，
  必须**先拆焊再补空格**，两条颠倒就白干（自测里踩到）。
  ⚠️ 逗号规则只锚「术语紧邻术语」，写成通用 `,(?=[A-Z])` 会误伤缩写/编号。

## 三、⭐ 修好两个「验收脚本自己骗人」的度量缺陷

这两个都是**假阳性/失真**，不修就会一直误导排查方向：

### ① ② 指标：`<!DOCTYPE html>` 被当成「专名+术语粘连」（1331 页全中）

### 7.3 ⭐ 本轮新增的工程教训（都值得抄）

1. **⭐⭐ 前台跑「全站扫描」会被 SIGTERM(137) 杀掉，连 `print` 都留不下。**
   实测：`bump_assets_ver.py --dry-run`、任何一个「读 1355 个 html」的循环，
   前台跑必死（无输出、exit 137）；同一条命令 `run_in_background` 就正常（2m07s）。
   页面上千后**一律后台跑**，这不是"慢不慢"的问题，是会不会被杀的差别。
   （排查过程还确认了：不是 symlink/FIFO、不是大文件、不是 OOM。）
2. `bump_assets_ver.py` 原来用 `ROOT.rglob("*.html")` —— `.git` 338M + `outputs` 143M
   会被一起遍历。改 `os.walk` + 剪枝（`.git/outputs/node_modules/__pycache__`）。
3. **机翻/批处理脚本的自伤写法要当场断言**：`add_prefix()` 写成
   `'%shref="%s%s"' % (m.group(1), …)` 而 `m.group(1)` 已含 `href="` →
   产出 `href="href="../x.html"`，1078 文件 / 10780 处静默损坏（目录计数看着还正常）。
   两道闸门：改完函数加 `assert 'href="href="' not in out`，并全站
   `s.replace('href="href="','href="')` 修复 + 复扫 `href="href="|class="class="|src="src="` 归零。
   教训：**用 `repr()` 抽 3 个样本肉眼确认**，比看统计数字管用。
4. **`/x/index.html` 与 `/x/` 是两套 URL**：canonical/hreflang/og:url/sitemap/内链
   必须统一成目录形式 `/x/`（本机共 287 + 63 + 86 处），否则 canonical 指向一个会被
   301 的 URL、hreflang 目标"不存在"、站内出现同一内容的两个 URL。
   `vercel.json` 同步补 7 条 `/…/applications/index.html → /…/applications/` 的 301。
5. **审计脚本自己要能被审计**：`url_path()` 对**裸 `index.html`** 没做 `/` 映射，
   导致首页被误报「未进 sitemap」「hreflang 互指不对称」（假报）。加
   `if p == "index.html": return "/"`。
6. **显式 `noindex` 的孤立页要豁免**：`product.html` 是 noindex 的 JS 模板，
   不该要求 hreflang 齐全 / JSON-LD / 进 sitemap。审计脚本已加 `noindex` 判定。
7. **JSON-LD 自动生成要用 DOM 结构取字段**：首版用
   `<a href="…blog/xx.html">(.*?)</a>` 抓卡片全文，把徽标 + 标题 + 中英双语描述 + "Read →"
   全塞进 `ListItem.name`。改成先 `class="post-card"` 定位、再取块内 `<h3>`/`<p>`。
   （另：正则里写 `"blog\.html#blog"` 带引号会匹配不到 `…com/blog.html#blog` —— 引号不在那儿。）
8. **双语块双 h1 要当"设计"而不是"bug"**：站点约定 EN 文章页 `.lang-en` + `.lang-zh`
   各带一个 `<h1>`，`.lang-zh` 默认 `display:none`。审计报「多 h1」时应说明，
   不要为了清零去改结构（会破坏 zh 块结构对等的校验）。
