## 一、画册 PDF 的实测事实（决定了哪些技能有用）

| 项 | 实测值 | 含义 |
|---|---|---|
| 页数 | 42（正文 p5–p42，38 页） | — |
| **文字层** | `get_text()` = **0 字符** | 纯位图，无文本对象 |
| **矢量图** | `get_drawings()` = **0 个** | 无矢量线条 |
| **每页内嵌图** | **2 张**：一张已放置（整页）、一张**未放置** | 未放置那张是背景底版，**不是隐藏的原图** |
| 放置图原生像素 | **~2397 × 2433**（各页 2394–2401 浮动） | 与 pt 1:1，**再放大渲染只是插值** |
| 压缩率 | 0.035–0.067 B/px（JPEG q≈60–75） | 中等压缩，有轻微块效应 |
| 页面底色 | 空白区 min 通道**中位 246**、75% 像素 <250 | **不是纯白**，是浅灰渐变 |
| 背景干扰 | 一层**淡人物剪影**（中位 241、p10 203） | 阈值法会把剪影并进产品 |
| 版面 | 每页 2 台（p37/p39/p41 为左右同 y 交错；p28–p33 为上下紧邻） | 决定了自动定位的难度 |

**分辨率天花板**：紧裁一台产品 ≈ **1500–1900 px 长边**。
比我在 v2 里设的「≥2000px」门槛低约 25%，但**远超网站用图所需**（1200–1600px 足够）。

## 二、GitHub 技能调研：关键是要先把它们分成两族

搜到的技能/工具分两族，**只有第二族对画册有效**：

### A 族 —— 内嵌图提取（对画册=**死路**）

| 项目 | 机制 | 对画册的结果 |
|---|---|---|
| `anthropics/skills` → **`pdf`**（**本机已内置**） | `pdfimages` / PyMuPDF 抽内嵌图 | ⛔ 每页只能拿到**整页那一张** |
| `jiehai4/PDF-Skill` | PyMuPDF 抽图 + NLP | ⛔ 同上 |
| `dobachi/claude-skills-marketplace` → `document-figures` | 内嵌图 + **页级**渲染 + Figure Ledger | ⛔ 页级，不是区域裁剪 |
| `PatrikBak/MathComps` → `extract-figures` | 矢量图元聚类 | ⛔ **README 明确写**："Do NOT use for raster/scanned PDFs (it only handles vector drawings)"，且实测 `drawings=0` |
| `abhiramkrishnayanam/PDF-Image-Exctractor` | PyMuPDF 渲染 + **OpenCV 轮廓检测** | ⚠️ 思路最接近，但其 README 自承「文字/噪声误检」——**会撞上我下面实测到的同一个坑** |

### B 族 —— 版式检测 / 视觉定位（**正解**）

| 项目 | 机制 | 备注 |
|---|---|---|
| `Deng-GuiFeng/Paper2PPT` → **`extract-pdf-figure`** | **Qwen3-VL grounding** 出 bbox → 裁剪 + 迭代质检 | ✅ 最贴合；需 OpenAI 兼容 API key |
| `TingdeLiu/Tyndall-Skills` → **`pdf-figure-extractor`** | **Florence-2 目标检测**（`yifeihu/TF-ID-base`） | ✅ 纯本地；需 conda + transformers/torch |
| `opendatalab/MinerU`（~30k★） | PP-DocLayout 版式检测；**自动识别扫描版并启 OCR** | ✅ 最成熟，但依赖重（PaddlePaddle） |
| `docling-project/docling`（IBM，~20k★） | 版式模型 → picture 元素 | ✅ 企业级，偏重 |
| `datalab-to/marker`（~19k★） | Surya 版式 → 图片带上下文 | ✅ 通用性强 |
| `PaddlePaddle/PaddleOCR` → `PP-StructureV3` | 版式检测 + 图块抽取 | ✅ 中文文档强 |
| `perasyudha/Nyxora`、`AjayRajan05/VoiceOS`、`NousResearch/hermes-agent` → **`ocr-and-documents`** | pymupdf vs **marker-pdf** 路由的技能封装 | ⚠️ 重点是正文/表格，图片是附带 |

**结论：** A 族解决不了我们（它们抽的是「内嵌对象」，而我们的内嵌对象就是整页）；
B 族是正解，但它们解决的是**「页面上哪个区域是图」**这个定位问题。

## 三、自研路线实测：三版演进 + 量化指标

我直接用 PyMuPDF + numpy（本机已有 `ocrmac` 提供文字 bbox）试了三条路：

| 版本 | 思路 | 结果 |
|---|---|---|
| **v1** | 非白掩膜 + 膨胀 + 最大连通域 | ⛔ 产品与规格文字在 x 上相邻/重叠 → bbox 近整页 |
| **v2** | + **OCR 文字掩膜**（挖掉文字框） | ⚠️ 文字掩膜**有效**，但背景淡剪影（203）仍被并进来 |
| **v3** | + **严格暗阈值 `min<120`** + 只取产品暗核 + 外扩补浅色部件 | ⚠️ 明显改善，但仍不稳定 |

### v3 全量指标（38 页 / 69 台）

| 指标 | 值 |
|---|---|
| 台数全对页 | **26 / 38**（68%） |
| 与规格文字重叠 | **42 / 69 台**（61%） |
| 裁图数 | 56 张 |
| 宽中位 / 高中位 | 1707 px / 1299 px |
| 长边 ≥1500 | **41 / 56 张**（73%） |
| 长边 ≥1000 | 51 / 56 张（91%） |

### 参数是**结构性两难**，不是没调好

| 邻框合并间距 gap | 后果 |
|---|---|
| 小（2%） | 单台产品**裂成多块** → p12 出 7 块（应 1 块）、p16 出 4 块、p18 出 6 块 |
| 大（5%） | **同页两台粘成一块** → p29–p33 各只得 1 块且尺寸近整页（2150×2298） |

根因：**有些页「两台之间的距离」小于「单台自身碎片之间的距离」**。
任何单一阈值都必然在两类页面上之一失败 —— 这正是 B 族要上检测模型的原因。

### 实际产出（联系表已存档）

`reports/pilates_catalog_crop_contact_sheet_20260926.png`（56 张，8 列）
目视结论：**约一半可直接用**，其余两类缺陷：
1. **左侧规格文字粘连**（p4/p6/p7/p10/p14/p19/p20/p21/p22/p27/p28…）
2. **带上背景渐变或人物剪影**（p9/p13/p17/p24/p25/p29/p32/p33/p35/p40/p41）

## 四、判定

| 问题 | 判定 |
|---|---|
| 画册能提出产品图吗？ | ✅ **能**。已验证导出 1630×901 纯白底无水印成品 |
| 分辨率够网站用吗？ | ✅ 够（长边 1500–1900，网页 1200–1600 即达标） |
| 能**自动**裁准吗？ | ⛔ **不能**（68% 页台数对 / 61% 台文字粘连）。需检测模型 或 逐张复核 |
| 需要装 GitHub 上的技能吗？ | **取决于你要哪一档**，见下 |
| 还要向器械厂要图包吗（Q1）？ | ✅ **要**，但降级为「替换更好的图」，不再是阻塞 |

### 三条可选路线

| 路线 | 做法 | 代价 | 产出质量 |
|---|---|---|---|
| **① 自研 + 逐张复核**（最省） | 用现有 v3 脚本当**初筛**，我逐张看图修 bbox | 69 张人工复核，无新依赖 | 好，可控 |
| **② 装 B 族技能**（推荐先试轻的） | `pdf-figure-extractor`（Florence-2 本地）或 `extract-pdf-figure`（Qwen3-VL，需 API key） | 需装 torch/transformers（~3–5GB）或 API 额度 | 定位更准，但**它不知道「文字不属于图」**，仍可能有文字粘连 |
| **③ 先只上表、图后补** | 69 台先只有规格表 + 文案，图位留白 | 0 代价 | 器械页无图转化率差 |

> 注意：B 族是「找出页面上的图区域」，而我们的画册里**规格文字紧挨产品**，
> 通用模型可能把文字一起框进去（`extract-pdf-figure` 的「full-content capture」模式尤其如此）。
> **所以装技能不一定比路线①省事** —— 这是必须说清的。
